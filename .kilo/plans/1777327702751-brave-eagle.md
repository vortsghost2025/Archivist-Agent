# Plan: Cross-Lane Broadcast Verdict System

## Problem Statement
Work completed in one lane (e.g., Archivist refreshes heartbeats + passes recovery) is not visible to other lanes (e.g., Library still shows 1/4 green). Mailboxes prove intent but don't provide a shared, timestamped "state of the world" artifact that all lanes consume.

**Root cause:** No single source of truth for cross-lane verdicts. Each lane operates on stale cached state until explicitly bridged.

## Goal
Create a canonical broadcast artifact that:
1. Records the **current verdict** (e.g., `RECOVERY_PROVEN`, `CONFLICTED`, `GREEN`) with timestamp
2. Is **written by any lane** after state-changing work (recovery suite, sync, major fix)
3. Is **read by all lanes** at startup and on periodic intervals
4. Enables Library (and other lanes) to display accurate, current status without manual relay

## Solution Components

### 1. Broadcast Verdict Schema (`lanes/broadcast/last-recovery.json`)
```json
{
  "schema_version": "1.0",
  "timestamp_utc": "2026-04-27T20:40:00Z",
  "verdict": "RECOVERY_PROVEN",
  "suite_version": "recovery-test-suite-v2.1",
  "lane_liveness_detail": {
    "archivist": { "status": "alive", "last_heartbeat": "2026-04-27T20:39:00Z" },
    "kernel": { "status": "alive", "last_heartbeat": "2026-04-27T20:38:00Z" },
    "swarmmind": { "status": "unknown", "last_heartbeat": null },
    "library": { "status": "conflicted", "last_heartbeat": "2026-04-27T18:00:00Z", "reason": "stale_cache" }
  },
  "run_by": "archivist",
  "git_sha": "abc123...",
  "idempotency_key": "recovery-2026-04-27T20:40Z",
  "affects_lanes": ["archivist", "kernel", "swarmmind", "library"],
  "evidence_path": "lanes/archivist/outbox/recovery-run-20260427.json"
}
```

### 2. Write Path: Trigger on Recovery Suite Completion
- Modify `scripts/recovery-test-suite.js` (or wrapper) to:
  - On exit with `PROVEN` status, call a new utility `scripts/write-recovery-verdict.js`
  - This utility writes `lanes/broadcast/last-recovery.json` atomically
  - Also logs to `lanes/broadcast/recovery-history/` for audit trail

### 3. Read Path: Lane Startup + Periodic Refresh
- Each lane's startup routine (e.g., `scripts/lane-worker.js`, `scripts/heartbeat.js`):
  - Read `lanes/broadcast/last-recovery.json`
  - If file is missing or older than N minutes (configurable, default 5):
    - Re-run the cheap check (heartbeat-only probe or recovery suite)
    - Update the broadcast file with new verdict
- Library dashboard explicitly reads this file first before inferring status

### 4. Correlation + Idempotency
- All lane messages that affect multiple lanes include:
  ```json
  {
    "affects_lanes": ["archivist", "kernel", "swarmmind", "library"],
    "idempotency_key": "recovery-2026-04-27T20:40Z"
  }
  ```
- Lane workers check idempotency key before processing to avoid duplicate work

### 5. Schema Versioning on Shared Behavior
- Add `protocol-version.json` in `lanes/broadcast/`:
  ```json
  {
    "recovery_suite": "2.1",
    "heartbeat_format": "1.3",
    "verdict_schema": "1.0"
  }
  ```
- Mismatches become visible (e.g., lane refuses to process if version mismatch)

## Success Criteria
- [ ] Library lane shows accurate status (4/4 green) within 5 minutes of Archivist completing recovery
- [ ] No manual relay required for cross-lane state sync
- [ ] Verdict file is present and schema-valid after recovery suite runs
- [ ] Lane workers correctly read and act on verdict file
- [ ] Idempotency prevents duplicate processing
- [ ] Protocol version mismatches are detected and reported

## Rollback Plan
- If issues arise, revert `scripts/write-recovery-verdict.js` and lane worker changes
- Broadcast file is non-destructive; lanes can fall back to old behavior if file missing

## Open Questions / Tradeoffs

1. **Storage location**: Should verdict file be in `lanes/broadcast/` (shared) or per-lane `lanes/{lane}/inbox/`?
   - **Recommendation**: `lanes/broadcast/` for shared visibility

2. **Refresh interval**: How often should lanes re-check the verdict file?
   - **Recommendation**: On startup + every 5 minutes (configurable)

3. **Atomic writes**: Need to ensure atomic write utility works across Windows symlinks
   - **Recommendation**: Use `fs.rename` pattern (atomic on Windows)

4. **Who owns the verdict?**: Archivist? Kernel? Any lane?
   - **Recommendation**: Any lane can write; last-write-wins with idempotency tracking

5. **History retention**: How long to keep `recovery-history/` logs?
   - **Recommendation**: Last 100 runs or 7 days, whichever is longer
